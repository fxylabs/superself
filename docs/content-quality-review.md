# 콘텐츠 품질 검토 기준

- Status: working standard v0.2
- Last updated: 2026-08-24
- English: [content-quality-review.en.md](content-quality-review.en.md)

## 무엇을 확인하는가

이 검토는 글쓴이가 사람인지 AI인지 판별하지 않습니다. 대상 독자가 콘텐츠를 쉽게 이해하고 실제 판단이나 행동에 쓸 수 있는지 확인합니다.

- **쉽게 이해된다:** 독자가 다시 읽지 않고 자신의 상황, 새로 할 행동, 확인할 결과를 설명할 수 있습니다.
- **유용하다:** 콘텐츠를 본 뒤 실제 작업에서 판단을 내리거나 지원 범위 안의 절차를 끝낼 수 있습니다.
- **정확하다:** 사실, 명령, 출력이 근거 기록과 맞고 관찰과 추론이 구분됩니다.
- **필요한 것만 남는다:** 각 문장과 시각 자료가 이해, 행동, 확인 가운데 하나를 돕습니다.

짧거나 쉬운 단어를 썼다는 이유만으로 통과시키지 않습니다. 필요한 설명을 빼서 독자가 추측하게 만들면 이해하기 어려운 콘텐츠입니다. AI 탐지기, 금칙어 개수, 가독성 점수도 통과 근거로 쓰지 않습니다.

## 어디에 적용하는가

파일 종류가 아니라 독자에게 생기는 변화로 판단합니다. 다음 작업은 모두 이 검토를 거칩니다.

- 랜딩, 홈, 제품, 기능, 가격, 영업, 문의, 캠페인 페이지
- 공개 온보딩, 이메일, CTA, 폼, 빈 화면 문구
- 튜토리얼, 문서, 업데이트, 글, README, 릴리스 문구와 저장소 메타데이터
- 제목, 요약, 검색·소셜 메타데이터, 도식, 이미지, 애니메이션, 영상의 설명과 정보 순서
- 여러 공개 화면의 문구, 위계, 타이밍, 가독성을 바꾸는 공통 컴포넌트

내부 메모, 고치지 않은 제품·터미널 출력, 생성 파일, 공개 의미·순서·가독성·행동을 바꾸지 않는 코드 수정은 제외합니다. 법률, 보안, 개인정보, 접근성, 금전 검토가 필요한 콘텐츠는 해당 검토도 별도로 통과해야 합니다.

콘텐츠 단위는 파일 하나가 아니라 독자 결과 하나입니다. 한 랜딩페이지가 여러 컴포넌트와 메타데이터, 영상을 함께 쓴다면 하나의 기획서가 영향을 받는 파일과 화면을 모두 적습니다. 공통 컴포넌트가 여러 독자 결과를 바꾸면 각 결과를 함께 검토합니다.

에이전트는 모든 콘텐츠 작업에서 [content-quality-gate Skill](../.agents/skills/content-quality-gate/SKILL.md)을 먼저 읽습니다.

## 검토 범위부터 고정하기

검토 전에 아래 여섯 항목을 한 문단으로 적습니다.

1. 대상 독자와 독자가 처한 상황
2. 콘텐츠를 본 뒤 내려야 할 판단 또는 끝내야 할 행동 하나
3. 바뀌는 공개 파일과 독자가 따라 할 절차
4. 지원하는 입력, 환경, 제품 버전
5. 사실을 확인할 기록, 외부 출처와 시스템
6. 이번 검토에서 제외할 내용과 충분한 증거가 모였을 때 멈출 조건

검토자는 이 범위 밖의 새 기능, 모든 예외 처리, 제품 전체 설명을 요구해 발행을 막지 않습니다. 다만 지원 범위에서 실제로 생길 수 있는 보안, 개인정보, 법률, 금전, 복구할 수 없는 데이터 손실 위험은 차단합니다.

## 검토 절차

### 1. 독자 결과 확인

기획서에서 다음 네 문장을 찾습니다. 하나라도 없으면 본문 표현을 고치기 전에 기획서를 고칩니다.

- 독자는 지금 무엇을 하려는가?
- 어디에서 막히는가?
- 콘텐츠를 본 뒤 무엇을 다르게 판단하거나 실행하는가?
- 어떤 실제 기록이 그 판단을 뒷받침하는가?

### 2. 주장과 근거 확인

사실로 읽히는 문장을 모두 표시하고 실제 기록에 연결합니다. 직접 보지 못한 사용자 행동과 원인은 추론으로 표시하고 관찰 횟수와 가장 싼 반증 방법을 적습니다. 근거가 없고 독자의 행동에도 필요하지 않은 주장은 지웁니다.

### 3. 문장과 시각 자료의 역할 확인

제목, 문장, 표, 코드, 이미지, 영상 장면마다 아래 역할 하나 이상을 적습니다.

| 표시 | 역할 | 확인 질문 |
| --- | --- | --- |
| `C` | 상황 | 독자가 자기 문제를 알아보는 데 필요한가? |
| `E` | 근거 | 주장이나 결과를 실제 기록으로 확인하게 하는가? |
| `A` | 행동 | 독자가 무엇을 해야 하는지 분명한가? |
| `R` | 결과 | 행동 뒤 무엇이 보여야 하는지 알 수 있는가? |
| `D` | 판단 | 독자가 다음 단계나 완료 여부를 결정하게 하는가? |

역할을 붙일 수 없는 항목은 지우거나 고칩니다. 같은 역할과 정보를 반복하는 항목도 하나만 남깁니다. 제품명을 다른 제품명으로 바꿔도 그대로 성립하는 장점 문장은 실제 사건, 수치, 명령으로 바꿀 수 있을 때만 남깁니다.

### 4. 독자가 따라 할 절차를 그대로 실행하기

독자가 보게 될 폭과 재생 속도에서 콘텐츠를 엽니다. 명령은 지원 환경에서 다시 실행하고, 설명한 결과와 실제 출력을 대조합니다. 리뷰어가 설명을 보태지 않아도 각 단계의 행동과 결과를 찾을 수 있어야 합니다.

### 5. 작성자와 다른 리뷰어가 읽기

리뷰어에게 대상 독자, 지원 범위, 기대 결과를 줍니다. 누가 글을 썼는지는 검토 항목이 아닙니다. 리뷰어는 다음을 자기 말로 답합니다.

1. 이 콘텐츠는 누구의 어떤 상황을 다루는가?
2. 독자는 무엇을 다르게 해야 하는가?
3. 어느 문장이 사실이고 어느 문장이 추론인가?
4. 실행 뒤 무엇을 보고 성공 여부를 판단하는가?
5. 없어도 결과가 달라지지 않는 문장이나 장면은 무엇인가?

작성 에이전트는 자신이 쓴 콘텐츠를 `ready`로 판정하지 않습니다.

### 6. 타깃 독자에게 확인하기

새 메시지, 첫 튜토리얼, 새로운 시각 형식은 대상 독자 5명에게 확인합니다. 이미 검증한 구조에서 사실이나 명령만 바꾼 콘텐츠는 독립 리뷰와 실제 실행만 다시 합니다. 바뀐 부분이 독자의 이해나 행동에 새 위험을 만들 때 그 부분의 독자 확인도 반복합니다.

독자가 콘텐츠를 덮은 뒤 다음을 관찰합니다.

- 자신의 문제와 맞는 콘텐츠인지 설명하는가?
- 핵심 순서를 자기 말로 다시 말하는가?
- 첫 행동과 확인할 결과를 찾는가?
- 정해진 절차를 리뷰어의 추가 설명 없이 끝내는가?
- 멈추거나 되읽거나 다른 뜻으로 이해한 지점은 어디인가?

새 메시지나 첫 형식은 5명 중 4명이 핵심 판단과 첫 행동을 설명해야 합니다. 실행 가능한 튜토리얼은 5명 중 4명이 정해진 절차를 추가 설명 없이 끝내야 합니다. 같은 핵심 지점에서 2명 이상 막히면 문장이나 순서를 고치고 다시 확인합니다. 사실 오류와 재현 실패는 인원수와 관계없이 차단합니다.

## 한국어 번역투 검토

한국어는 영어판을 옮겨 쓰지 않고 같은 기획서와 사실표에서 따로 씁니다. 번역투는 특정 어휘 하나만의 문제가 아닙니다. 영어식 주어 반복, 명사화, 피동 구조, 정보 순서가 남아 독자가 뜻을 다시 조립하게 만드는 경우를 함께 봅니다.

### 먼저 찾을 흔적

- 행위자가 사라진 피동문과 `~에 의해`, `~되어지다`
- `수행하다`, `진행하다`, `제공하다`, `지원하다`가 구체적인 동사를 대신한 문장
- `~를 통해`, `~에 대한`, `~의 경우`, `~하는 데 있어`가 이어지는 문장
- 영어 명사구를 따라 `~의 ~의`, `및`, 괄호 설명을 겹친 문장
- 결론이나 조건이 뒤에 있어 끝까지 읽어야 행동을 알 수 있는 문장
- 한국어에서 생략해도 분명한 주어와 대명사를 매 문장 반복한 경우
- 영어판의 문장 수와 순서를 그대로 맞춘 흔적

이 목록은 자동 탈락 기준이 아닙니다. 표시된 문장을 실제 독자의 말과 더 짧은 동사로 다시 써 보고, 뜻과 행동이 더 빨리 드러나는 쪽을 선택합니다.

### 한국어 전용 검토 순서

1. 영어판을 닫고 기획서의 독자 상태, 사실표, 실제 명령만 보고 한국어 초안을 씁니다.
2. 문장마다 누가 무엇을 하는지 찾고, 행위자가 중요하면 앞에 둡니다.
3. `명사 + 하다`와 피동 표현을 실제 행동 동사로 바꿔 읽어 봅니다.
4. 조건은 행동 앞에, 확인할 결과는 명령 바로 뒤에 둡니다.
5. 대상 독자 1명에게 문장을 읽게 합니다. 어색한지 묻는 대신, 무엇을 하라는 뜻인지 자기 말로 설명하게 합니다.
6. 한국어판과 영어판의 문장 수와 접속 구조가 계속 같으면 별도 작성 원칙을 어겼는지 확인합니다.

번역투 후보 목록은 검토를 시작하는 도구입니다. 최종 근거는 독자가 더 적게 되읽고, 같은 뜻을 말하며, 필요한 행동을 끝냈다는 관찰입니다.

## 판정과 기록

평균 점수로 판정하지 않습니다. 높은 문체 점수가 사실 오류나 실행 실패를 덮을 수 있기 때문입니다.

- `revise`: 핵심 판단, 사실, 명령, 결과, 독자가 따라 할 절차 가운데 하나가 실패함
- `ready`: 정한 범위의 사실과 실행이 맞고, 독립 리뷰와 필요한 독자 확인을 통과함
- `validated`: 발행 뒤 실제 독자의 이해나 사용 행동이 관찰됨

`approved`는 기획서 상태입니다. `ready`는 제작된 콘텐츠의 발행 전 판정입니다. `validated`는 발행 뒤 얻는 근거입니다. 세 상태를 서로 대신 쓰지 않습니다.

각 검토는 `docs/content-reviews/<slug>.<lang>.md`에 남깁니다.

```markdown
# <콘텐츠> 품질 검토

- Brief revision:
- Content commit:
- Reviewer:
- Reviewed at:
- Supported reader and path:
- Verdict: revise | ready | validated

## 검토 범위
## 주장과 근거
## 문장·시각 자료 역할
| 위치 | 역할 C/E/A/R/D | 독자가 얻는 것 | 발견 | 조치 |
## 실제 실행
## 독립 리뷰 답변
## 독자 확인
## 남은 가설과 다음 확인
## 충분한 근거와 중지 조건
```

## 기준을 개선하는 법

한 문서의 문제를 곧바로 모든 콘텐츠의 규칙으로 만들지 않습니다. 먼저 해당 콘텐츠를 고치고 관찰을 남깁니다. 같은 문제가 여러 콘텐츠나 여러 독자에게 반복되거나, 한 번의 실패라도 비용이 큰 경우에만 공통 규칙을 제안합니다.

규칙을 바꿀 때는 아래를 기록합니다.

- 어떤 관찰 때문에 바꾸는가?
- 몇 번, 어느 언어와 형식에서 관찰했는가?
- 새 규칙이 막아야 할 실패는 무엇인가?
- 가장 싼 반증 방법은 무엇인가?
- 어느 기존 규칙을 없애거나 좁힐 수 있는가?

리뷰 결과를 바꾸지 않는 금칙어나 점검은 지웁니다. 발행 뒤에는 질문, 잘못된 되말하기, 단계 이탈, 실행 성공, 다음 행동을 관찰에 추가합니다.
