현재 근거로 일반 시장의 실패 원인을 단정하지 않습니다. 튜토리얼은 실제 run에서 확인된 사실과 사용자가 실행할 절차만 말합니다.

## 1. 소비자는 지금 어떤 상태인가?

- 1차 타깃은 AI 에이전트의 결과가 요구와 달라 한 번 이상 다시 고친 사람입니다.
- 2차 타깃은 코드 편집기나 터미널에서 에이전트에게 작업을 맡기려 하지만, 언제 무엇을 검토해야 하는지 모르는 사람입니다.
- 에이전트가 바로 구현을 시작하는 흐름에는 익숙할 수 있지만, 계획을 별도 상태로 등록하고 승인하는 흐름은 모른다.
- 결과가 요구와 다를 때 어느 시점에서 무엇을 검토했어야 하는지 판단 기준이 없다.
- Superself나 Company State Runtime을 안다고 가정하지 않는다.

## 2. 무엇을 시도하고 어떤 문제를 겪는가?

확인된 문제는 실제 실행의 v1에 구현 범위와 fragment 처리 규칙이 빠졌다는 점입니다. 구현 뒤 발생했을 수정 비용은 관찰하지 못했으므로 가설로 둡니다.

긴 프롬프트 작성, "주의해서 해 달라"는 추가 지시, 구현 후 diff 검토는 현재 가설입니다. 독자 관찰 전에는 도입부에서 보편적 행동처럼 말하지 않습니다.

## 3. 왜 그런 일이 벌어지는가?

이 튜토리얼이 다루는 원인은 좁습니다.

- 구현 전에 사람이 읽을 계획이 독립된 작업 상태로 남아 있지 않다.
- 검토하지 않은 계획으로도 에이전트가 바로 시작할 수 있다.
- 수정 전 계획, 승인된 계획, 구현 보고가 한 작업 ID로 이어지지 않는다.

`w-cs7dj` 실행에서는 첫 번째 항목 두 개를 `work propose`의 review 상태와 start gate로 바꿨고, 세 번째 항목을 같은 ID의 revision과 report로 확인했습니다. 이것이 모든 에이전트 실패의 원인이라고 주장하지 않습니다.

## 4. 우리는 어떻게 해결하는가?

사람과 에이전트가 같은 work를 봅니다.

1. 에이전트가 구현 전에 계획 전체를 `work propose`로 남긴다.
2. 사람 또는 별도 리뷰 에이전트가 계획을 읽는다.
3. 결함이 있으면 같은 ID에서 `work revise`로 고친다.
4. 사람이 검토한 revision만 `work accept`하고 에이전트가 시작한다.
5. 에이전트가 커밋과 검증 결과를 report에 남기고, 사람이 완료를 판단한다.

이 튜토리얼은 판단이 필요한 작업 하나의 수동 리뷰를 가르칩니다. 모든 반복 작업을 사람이 하나씩 승인하는 운영 방식으로 확대하지 않습니다.

## 5. 어떻게 이해와 채택으로 이어지게 하는가?

독자의 인지 순서를 다음과 같이 잡습니다.

1. **알아봄:** 구현 뒤 누락을 발견하면 이미 만든 결과를 다시 고쳐야 한다.
2. **새 판단 기준:** 구현 전에 계획을 읽고 승인할 시점이 필요하다.
3. **전체 흐름:** 시각 재생은 누가 계획을 쓰고, 검토하고, 승인하고, 완료를 판단하는지만 보여 준다.
4. **직접 확인:** 승인되지 않은 v1의 start가 막히는 실제 출력을 본다.
5. **수정:** 결함 두 개가 v2에 어떻게 반영됐고 ID가 유지됐는지 확인한다.
6. **실행과 증거:** accept 뒤 시작하고, report의 커밋과 테스트를 계획에 대조한다.
7. **첫 채택:** 다음 10분짜리 에이전트 작업 하나에서 같은 순서를 사용한다.

시각 재생은 제품 화면이나 실행 증거 역할을 하지 않습니다. 역할과 상태 변화의 순서를 먼저 이해시키는 설명 자료입니다. 원본 출력과 명령은 각 단계와 출처에 둡니다.

## 소비자의 머릿속에 남길 자리

- 보기 전 생각: 에이전트에게 요구사항을 전달한 뒤 결과가 맞기를 기다린다.
- 보고 난 뒤 판단: 구현 전에 에이전트의 계획을 work에서 검토하고, 승인한 계획과 결과를 같은 ID에서 대조할 수 있다.
- 기억할 한 문장: **에이전트에게 일을 맡길 때는 구현 전에 계획을 work에 남겨 함께 검토한다.**
- 실제 증거: v1의 결함 두 개, 차단된 start, 같은 `w-cs7dj`의 v2, `fea913a` report와 settled evidence.
- 공통 연상과의 연결: 이 사례에서 프로젝트 상태는 승인된 계획, 실행 상태, report와 evidence다. 사람과 에이전트가 같은 상태를 본다.

## 범위

- 포함: work 하나, 계획 revision 하나, 사람의 승인, 에이전트의 실행과 report, 완료 판단.
- 제외: 메모리 주장, Company State Runtime 전체 설명, 다중 work 운영, 자동 승인 정책, 대규모 에이전트 검토 대기열, 제품 기능 목록.

## 기획 승인 뒤 바꿀 콘텐츠

- 긴 첫 문단을 독자의 문제와 새 행동을 설명하는 두세 문장으로 바꾼다.
- 영상 아래 제작 시간 설명을 없애고, 영상이 보여 주는 실제 상태 변화만 한 문장으로 적는다.
- 각 단계가 독자의 판단 하나로 끝나는지 다시 확인한다.
- 한국어와 영어는 이 기획서와 fact table에서 각각 작성한다.
- 실제 프롬프트와 CLI 출력은 고치지 않는다.

## 성공 확인

콘텐츠를 본 사람이 문서를 다시 보지 않고 아래 질문에 답할 수 있어야 합니다.

1. 계획은 언제 work에 등록하는가?
2. 승인되지 않은 계획은 왜 시작되지 않는가?
3. 계획을 고칠 때 왜 같은 work ID를 유지하는가?
4. 완료 전에 report에서 무엇을 확인하는가?

첫 번째 검토에 참여할 대상 독자 5명에게 이 네 질문과 "다음 에이전트 작업에서는 무엇을 다르게 하겠는가"를 묻습니다. 4명 이상이 계획 등록 → 리뷰 → 승인 → report 확인 순서와 첫 행동을 설명해야 합니다. 두 명 이상이 같은 지점에서 막히면 도입과 단계 순서를 고치고 다시 확인합니다. 실행 가능한 초안이 나오면 4명 이상이 추가 설명 없이 정해진 절차를 끝내는지도 확인합니다.
